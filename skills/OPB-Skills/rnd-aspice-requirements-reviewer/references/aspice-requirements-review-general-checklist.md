# ASPICE 需求通用评审检查清单

> 本检查清单适用于所有ASPICE需求评审场景，包括SYS.1客户需求、SYS.2系统需求和SWE.1软件需求。
> 版本：1.0
> 最后更新：2026-02-02

---

## 1. 完整性评审 (Completeness)

### 1.1 功能覆盖
- [ ] **CMP-001** 是否覆盖了所有用户场景和操作流程
- [ ] **CMP-002** 是否定义了所有的性能需求（响应时间、吞吐量、并发数等）
- [ ] **CMP-003** 是否定义了非功能需求（安全性、可靠性、可维护性等）
- [ ] **CMP-004** 是否识别并定义了容错相关操作
- [ ] **CMP-005** 是否识别并定义了操作时间限制
- [ ] **CMP-006** 是否定义了需求的验证准则
- [ ] **CMP-007** 每个版本需发布的功能是否在需求里都有对应体现

### 1.2 环境与接口
- [ ] **CMP-008** 是否充分分析了需求的运行环境
- [ ] **CMP-009** 接口需求是否完整定义（与硬件、其他软件模块的交互）
- [ ] **CMP-010** 边界条件和异常情况是否被充分考虑
- [ ] **CMP-011** 与其他系统/子系统的接口是否完整定义

### 1.3 安全与可靠性
- [ ] **CMP-012** 功能安全需求是否充分考虑（ASIL等级）
- [ ] **CMP-013** 信息安全/网络安全需求是否充分考虑
- [ ] **CMP-014** 可靠性需求是否明确（故障处理、降级策略）

---

## 2. 正确性评审 (Correctness)

### 2.1 准确性
- [ ] **COR-001** 是否每条需求都进行了功能的准确描述
- [ ] **COR-002** 是否所有性能目标都有恰当的定义
- [ ] **COR-003** 内部引用是否都正确
- [ ] **COR-004** 技术方案是否可行，是否存在物理或技术上的矛盾

### 2.2 合规性
- [ ] **COR-005** 是否符合相关的法规标准（如GB、ISO、UN Regulation等）
- [ ] **COR-006** 性能指标是否合理且可实现

---

## 3. 清晰性评审 (Clarity)

### 3.1 语言表述
- [ ] **CLR-001** 是否不存在主观的、模糊的或者其他可能导致不确定的语言描述
- [ ] **CLR-002** 是否所有的需求描述都采用了简明的格式没有语法错误
- [ ] **CLR-003** 是否每个需求都使用了统一的术语进行描述
- [ ] **CLR-004** 数值型要求是否给出具体的量化指标和容差范围

### 3.2 常见模糊词汇检查
以下词汇应避免使用或需要量化：
- "适当"、"合理"、"尽可能"、"必要时"、"及时"
- "快速"、"流畅"、"用户友好"（未量化）
- "低延迟"（应改为具体数值如"延迟<100ms"）
- 缺少单位的数值

---

## 4. 可行性评审 (Feasibility)

- [ ] **FEA-001** 是否定义了开发约束
- [ ] **FEA-002** 需求开发时是否关注了可行性约束条件
- [ ] **FEA-003** 是否有不可实现的需求
- [ ] **FEA-004** 是否每条需求都与其开发实施人员进行了确认

---

## 5. 必要性评审 (Necessity)

- [ ] **NEC-001** 是否所有需求都能追溯到最原始的需求（客户需求）或其他相关方输入
- [ ] **NEC-002** 是不是每项需求都在项目范围内

---

## 6. 可测试性评审 (Testability)

- [ ] **TST-001** 验证准则是否清晰，可指导后续测试用例编写
- [ ] **TST-002** 是否可以根据需求写出测试用例，创建符合预期的用户场景
- [ ] **TST-003** 每条需求是否可以通过测试或分析进行验证
- [ ] **TST-004** 验收标准是否明确和可度量

---

## 7. 一致性评审 (Consistency)

### 7.1 内部一致性
- [ ] **CON-001** 是否所有有关联的需求都在文档中的同一部分进行了适当的描述，并且文档结构合理
- [ ] **CON-002** 文档中是否存在相同对象的描述术语不一致
- [ ] **CON-003** 文档中是否存在相同对象的特性描述不一致
- [ ] **CON-004** 文档中是否有逻辑冲突的活动描述
- [ ] **CON-005** 文档中是否有技术冲突的活动描述

### 7.2 外部一致性
- [ ] **CON-006** 需求描述是否与上游需求保持一致

---

## 8. 可追溯性评审 (Traceability)

- [ ] **TRC-001** 每条需求是否有唯一标识符
- [ ] **TRC-002** 是否所有需求可以追溯回其规格定义的源文档或上游需求
- [ ] **TRC-003** 是否建立了向上和向下的追溯关系
- [ ] **TRC-004** 上游引用是否完整且正确
- [ ] **TRC-005** 下游引用是否已规划

---

## 9. 可变更性评审 (Modifiability)

- [ ] **MOD-001** 需求文档是否条理清晰、逻辑合理
- [ ] **MOD-002** 需求组织是否便于后续修改和扩展
- [ ] **MOD-003** 需求之间的依赖关系是否明确
- [ ] **MOD-004** 是否有版本标识和变更历史

---

## 10. 规范性评审 (Compliance)

- [ ] **REG-001** 是否使用了正确的模板，并且所有的需求、图形、表格都被标识了
- [ ] **REG-002** 封面信息、变更履历信息是否正确
- [ ] **REG-003** 参加评审的角色是否齐全，符合要求

---

## 问题严重等级定义

| 等级 | 定义 | 处理要求 |
|------|------|----------|
| **阻塞性 (Blocker)** | 导致需求无法实现、存在安全风险、或严重违反标准要求 | 必须修复，阻塞后续工作 |
| **重要 (Major)** | 可能导致实现偏差、测试困难、或影响需求追溯 | 建议修复，影响交付质量 |
| **一般 (Minor)** | 影响需求理解、可能导致沟通成本增加 | 可选修复，建议改进 |
| **建议 (Suggestion)** | 优化建议，提升需求质量但非必须 | 酌情处理 |

---

## 使用说明

1. 评审前：确认需求类型（SYS.1/SYS.2/SWE.1），选择适用的检查项
2. 评审中：逐项检查，记录发现的问题和对应的检查项ID
3. 评审后：汇总问题，按严重等级分类，输出评审报告
